# FileMate 首版代码审查

审查依据为技术方案 V2、内部 API 契约和首版实施计划。以下行号对应发现问题时的源码。审查覆盖 Python 服务、Windows 文件操作、PostgreSQL 状态转换、dsh 工具和 profile、浏览器业务面板、启动脚本、容器配置及现有测试。

## 审查发现

| 优先级 | 源码位置 | 触发条件与影响 | 修复与回归验收 |
| --- | --- | --- | --- |
| P1 | `services/filemate/plans.py:93`、`services/filemate/catalog.py:62` | 创建包含 A 和 B 的计划后，外部程序替换 A，用户重新扫描，仅编辑 B 的目标。修订会重新建立每一项的源文件指纹与条目 ID。如果 A 没有指向自身的版本化证据，用户可以批准并移动替换后的 A，尽管本次修改只涉及 B。 | 对保留项复用原条目 ID、源版本、身份及指纹，拒绝陈旧的原绑定。测试两条目计划在重扫后修改另一项，确认无法静默接受替换文件。 |
| P1 | `services/filemate/common.py:24`、`services/filemate/catalog.py:36` | 此 Windows 主机实测 `Straße.txt` 与 `Strasse.txt` 可同时存在，具有不同文件 ID。Python `casefold()` 将两者归并为相同索引键，扫描第二项时会覆盖第一项的元数据及正文。结果可能显示已扫描两项，却只检索到一项。相同键也用于根目录登记。 | 使用经文件系统确认的独立路径键。迁移现有索引键并重扫，确保版本升级可恢复已遗漏条目。测试两个名称独立搜索、内容读取和计划绑定。 |
| P2 | `services/filemate/plans.py:24`、`packages/harness-filemate/src/tools.ts:26` | 用户在面板执行后，聊天中已知的计划及任务都没有作业 ID。模型只具备按作业 ID 获取报告的工具，因而无法自行回答“刚才哪些文件移动失败了”。 | 在单计划或任务上下文返回关联作业 ID。验证仅持有计划 ID 的 Agent 能取得真实逐项报告，包括失败代码。 |
| P2 | `packages/harness-filemate/src/tools.ts:18`、`services/filemate/api.py:197` | 任务创建时记录了 dsh 会话 ID，但恢复任务工具要求提供精确任务 UUID。压缩或恢复后的会话只知道自己的会话 ID 时，没有工具可从 PostgreSQL 找回任务。 | 增加以实际 dsh 调用上下文识别当前会话的只读查找，返回近期任务供选择。测试两个会话、同一会话的两个任务，以及恢复时没有任务 UUID 的情形。 |
| P2 | `services/filemate/worker.py:32`、`services/filemate/plans.py:127` | 外部证据文档在作业排队后、执行前被替换。审批与入队阶段检查了该证据，Worker 仅重新检查源和目标，仍会按过时依据完成移动。 | 在开始文件变更前核对外部版本化证据。覆盖同一作业前序条目已按批准计划移动证据的情况，让这类正常执行可继续。 |
| P2 | `packages/harness-filemate/public/app.js:367`、`services/filemate/documents.py:136` | 计划引用较后页码、段落或字符范围时，审核人点击“打开证据文件”，面板总是读取第 0 个字符。PDF 和 DOCX 位置中的 `start` 是块内偏移，直接作为整篇偏移也不能定位该引文。 | 返回并保存全局字符范围，面板按引文位置打开对应版本。测试第二页引文位于第一个 4,000 字符窗口之后。 |

## 契约与质量判断

审批绑定、工具与管理令牌隔离、受审版本的重复执行返回同一作业、Windows 同盘无覆盖移动、持久化准备记录以及重启后的源/目标身份核对均能在实现与对应测试中追踪。dsh 工具集合没有审批或执行接口，业务面板使用宿主认证和明确分开的批准、执行动作。

本轮初审建议先修复表中问题，再验收完整的调查、审核与报告流程。两个 P1 涉及用户选择的具体文件，优先级高于展示细节。业务路径的测试应从原始会话和审核人实际拥有的标识出发，以覆盖跨界面交接。验收范围按首版约定，pgvector、OCR、Excel 留待后续阶段。此次审查直接验证了 Windows 文件名案例，其余表项来自实现、契约及已有测试的逐项核对。运行验证与修复后的状态以项目验证记录为准。
